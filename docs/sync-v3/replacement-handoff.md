# Independent-database writer handoff

Use an **empty, independently initialized Supabase project**, a distinct project ref and system identifier, new database passwords, new pool tenant, and new Supabase project/API/signing keys. Import only BaseballOS database objects and data. Exclude cluster globals, role passwords, physical backups, provider schemas and project configuration. The old project can continue to accept an old client without affecting the destination. A second database name on the old cluster shares roles and cannot provide this property.

The original-database path still requires proof that the managed pooler retired old frontends. PostgreSQL termination, RLS, stopping jobs, and ACL changes on owner-held tables cannot provide that proof. A production owner able to administer the replacement, or a former credential holder who also has independent organization administration, is outside a database-password fence. Limit destination administrative access to the operator, including management tokens and deployment secret access.

## Source inventory and expected impact

November 27 read-only inspection measured 15,903,034,515 bytes in production; 15,884,845,056 bytes were public relations. All 89 public tables have primary keys. The eight nonsync tables are identified in handoff_admin.EXCLUDED. Keep them all, including prospects. There were 5 application users, 20 follows, 5 audience subscribers and no editorial history rows. Auth users, Storage buckets and objects, Vault entries, Realtime publication tables, foreign servers, large objects and replication slots all counted zero. Public contains nine routines, and the two historical-repair schemas contain ten additional routines. Preserve routines, restricted execution privileges, triggers, primary and foreign keys, sequence state, edition IDs, historical snapshots and original evidence. The inspected table ACLs referenced postgres and service_role. Never import a source role's credential to satisfy an ACL.

The frontend uses the Render application API. The Flask API implements its own magic-link accounts and bearer tokens. Preserve its existing application signing, email, dashboard and domain settings. Keep the public API hostname and frontend base URL. Source project API keys grant no rights on a freshly keyed project. Before exposing the destination, check service-role RPCs and catalog privileges using the established fence, compare legacy and replacement access to sensitive account data, and test an existing application bearer session without logging it. If the production preflight discovers new Auth, Storage, Vault, Edge Function, webhook, foreign-server, Realtime or direct client dependencies, account for their data and callers before routing. Empty service tables alone cannot inventory external callers.

Keep encrypted temporary archive storage on the operator runner. A full 15.9 GB restore needs index and WAL headroom. Stop before exceeding a spending authorization. ## Exact order and authority

1. **Provisioning approval only.** Create a fresh, unrouted, same-region project. Restrict inbound database access to the runner at first, disable the destination Data API while importing, and protect all new keys. Record the original and new refs, CA-verified direct endpoints and PostgreSQL system IDs. On the destination verify an authorized new login and old-credential rejection on every enabled endpoint (direct, shared session/transaction and dedicated). Use protected secret files and independently verified TLS. Reject timeouts and circuit-breaker results. Confirm independently generated service credentials and reject the old project's token on the destination where relevant. No source rotation or pooler disruption is required.
2. **Private managed rehearsal.** Use the approved production-data handling boundary. Check PostgreSQL compatibility, installed extensions and available disk. Inventory non-provider namespaces, extensions, foreign servers, external functions, webhooks, replication and project features again. Compare object definitions and owners to the reviewed Alembic tree; never run unexpected source-supplied administrative code on the destination. Create no subscriptions, FDWs, dblink paths, source-owner memberships, or source-credential fallbacks. Run a full timed logical copy, restore, comparison and product smoke rehearsal off traffic. An unsuspended source can change during this rehearsal: compare rows at the dump's exported snapshot or use a quiescent isolated source copy. Only the final frozen comparison establishes handoff parity. Record wall time, archive size, disk/WAL high-water mark, memory and public catch-up time. Securely remove temporary archives after their retention window. Refuse cutover if the measured full procedure plus recovery margin exceeds the approved maintenance window.
3. **Pin the destination in a reviewed release.** Set PROJECT to the actual new ref and REPLACEMENT_CLUSTER to its verified system_identifier in backend/sync_v3/runtime_binding.py; keep ORIGINAL_PROJECT and ORIGINAL_CLUSTER pinned to the old system. Run both writer-fence paths on that exact commit. The currently shipped source pin disallows replacement activation. Destination preparation uses the original production-handoff commands with destination-only secrets. A physical clone carrying source credentials or system ID is ineligible. Prepare a fresh empty application target for the final replay; any cleanup must verify the new system ID, be confined to operator-created rehearsal objects and be explicitly authorized. Never clean a schema on the source. A provider-created public schema should be retained.
4. **Cutover approval, start of downtime.** Confirm the deployed build, current-date rollback root, measured duration, recovery margin and clock window. Archive the actual legacy selector and public edition via verify_public_sync_edition. Follow the [scheduler inventory and API service IDs](production-handoff.md). Suspend the five legacy crons, Actions fallback, manual sync/build entry points and API traffic; let active work finish. Preserve settings, secrets and commands for recovery. Serve maintenance for reads and writes, including telemetry. Verify traffic no longer receives success responses from the old API. Drain in-flight app requests and database transactions; account, follow and telemetry routes can otherwise lose acknowledged changes. Freeze application DDL and sequence use. Avoid a simultaneous source and destination service rollout.
5. **Acquire the source cutoff.** From a direct controlled session against the verified source ID, begin a transaction, set a finite lock timeout and take SHARE locks on every application table in deterministic schema/name order with NOWAIT. Keep the session open until public traffic transfers. This permits dump reads, orders pre-existing writes before the cutoff and blocks subsequent table DML. If acquisition fails, drain and retry. If the lock connection dies or the catalog changes before the routing decision, abort and discard the candidate. Also prohibit independent nextval/setval and DDL during the window and compare sequence state and application catalog just before release. The independent target credentials provide the lasting fence even after the locks are released.
6. **Copy and verify.** On a trusted runner use PostgreSQL 17-compatible clients, protected libpq service definitions, authenticated TLS and a private encrypted directory. Check the archive list before executing it. Retain all application ACLs; independently check effective grants and function ownership on the destination. Recreate missing reviewed privileges only, using fresh roles. An unexpected object or privilege stops the restore. For the currently inventoried source:

       umask 077
       pg_dump --dbname=service=baseballos_source --format=custom --schema=public --schema=roster_history_repair --schema=transaction_history_repair --file=product.dump
       pg_restore --list product.dump > full.list
       sed -E '/^[0-9]+; [0-9]+ [0-9]+ SCHEMA - public /d' full.list > restore.list
       pg_restore --dbname=service=baseballos_target --use-list=restore.list --exit-on-error --single-transaction --no-owner --role=postgres product.dump
       python -m scripts.verify_replacement_copy --source-service baseballos_source --destination-service baseballos_target --revision "$REV" > replacement.json

   The comparison uses read-only transactions and hashes every row in primary-key order. It compares sequence values and is_called, and routine bodies and attributes included in pg_get_functiondef. Separately compare catalog inventories, ACLs, RLS policies, constraints, trigger enablement and the public edition on the new API. Run before adding v3 objects or allowing destination product writes. Do not relax restore failures or reuse a partially populated destination.
7. **Prepare and activate on the new project.** Follow existing handoff steps 2–4 using the destination administrator, fresh dedicated runtime credentials and the scoped API login. The warm worker writes candidate data only. Keep legacy jobs stopped, the target legacy role NOLOGIN and free of sessions. On a privately routed instance of the tested API verify the old public fingerprint and the copy of the published snapshot/sync IDs. Then run from backend:

       python -m sync_v3.handoff_admin activate --revision "$REV" --receipt legacy.json --replacement-copy replacement.json
       python -m sync_v3.production cycle

   The replacement branch requires the actual connected target system ID, distinct and pinned source/target IDs and the exact revision. The common activation transaction checks the selector, revokes and audits effective legacy/service_role/RPC writer access, locks governed tables, and enables the scoped v3 roles. The operator controls the comparison receipt like the legacy predecessor receipt. Keep it with the source lock receipt, archive digest, credential challenges and deployment revision.
8. **Route and observe.** Route the existing Render API to the verified destination API role with verify-only migrations and AUTO_SYNC=false; omit the migration URL. Confirm all instances have been replaced before reopening ingress, including cached connections. Bind only the three fresh scoped runtime credentials to the existing Continuous cron with the tested v3 cycle. After the first promotion independently verify League, Tonight, all 30 Boards, the snapshot/sync/generation binding, historical routes, and a controlled account/follow and traffic write at the actual public URL. Check the previous signing key still verifies an application session. Confirm old pools can affect only the retired source; remove any outbound source-to-destination trust. Release source locks after routing has settled. Retain the original project offline to applications. Follow the existing 18-hour same-baseball-date observation and separately approve irreversible legacy retirement.
9. **Rollback.** Before target writes are exposed, abort, release the source lock and restore saved source routing/schedules after verifying the public root. Once the target accepts application writes, rollback stays on the replacement. Suspend v3 and execute begin-rollback, restore the pinned selector, verify the original public fingerprint and release only the fresh scoped legacy role using the commands in the existing handoff. Restore legacy scheduling against the **destination**, preserve all new account/follow/editorial/telemetry writes and verify them. A destination outage or suspected data corruption requires destination recovery or a verified reverse reconciliation before any return to the old DB. A blind rebind to the old database loses acknowledged writes. Retain backups on both sides.

Production cutover is a separate approval after the full-size managed rehearsal. Include the new project ref, actual release SHA, disk and cost quote, tested downtime and approved maximum, observation start/end, service bindings, scheduler changes and same-target recovery commands in that request. No step here retires production infrastructure.
